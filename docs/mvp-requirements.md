# 法律咨询 Agent MVP 需求与范围基线

文档状态：已确认
适用阶段：首月 MVP
当前进度与验收：[项目交接](../HANDOFF.md)、[M4课程MVP收尾](acceptance/m4-course-mvp-closeout-20261001.md)；[Run21验收](acceptance/rag-v2-final-acceptance.md)为M3历史记录。
目标环境：Windows 本地开发，最终通过 Docker Desktop 验收

本文定义四周MVP目标；实际完成范围以交接文档为准。

## 1. 项目定位

本项目是面向课程演示和本地部署的中国大陆法律咨询 Agent。系统通过大语言模型、法律知识检索和工作流编排，为用户提供一般法律信息、可追溯的案例或法条来源、案例检索结果以及常用法律文书草稿。

本项目不面向公众提供正式法律服务，不建立律师与用户之间的委托关系，不替代执业律师、司法机关或其他专业机构的判断。

## 2. 首月成功标准

首月完成以下业务闭环：

1. 用户注册并登录。
2. 用户输入问题，系统识别为法律问答、案例检索或文书生成。
3. 法律问答先检索知识库，再基于可用证据生成回答。
4. 回答展示案例或法条来源；依据不足时明确说明，不虚构来源。
5. 案例检索返回可筛选、可查看详情的结果。
6. 文书生成校验必填信息，生成可复制、可下载的 Markdown 或 TXT 草稿。
7. 多轮会话按用户和会话隔离，可查询和清空历史。
8. 前后端及依赖服务可以通过 Docker Compose 启动，并完成五个演示场景。

## 3. 用户角色

### 3.1 访客

访客可以：

- 查看首页、服务说明和免责声明。
- 注册账号或登录。
- 访问公开的健康检查接口。

访客不能访问法律问答、案例、文书和会话历史接口。

### 3.2 注册用户

注册用户可以：

- 发起普通或流式法律问答。
- 查看回答所依据的案例或法条来源。
- 检索案例并查看案例详情。
- 生成民事起诉状、民事答辩状和通用合同草稿。
- 复制或下载 Markdown/TXT 文书。
- 查看、继续和清空自己的会话。

用户只能访问自己的会话与生成记录。

### 3.3 本地运行者

本地运行者负责配置环境变量、启动服务、导入演示或真实资料并执行验收。本角色不是首月产品中的管理员角色，不提供管理后台或在线权限管理界面。

## 4. 核心业务场景

### S1：法律问答

- 示例：离婚时夫妻共同财产如何分割？
- 输入：问题文本、可选会话 ID。
- 处理：身份校验、意图识别、知识检索、证据筛选、回答生成、来源整理、风险提示。
- 输出：回答、意图、来源、会话 ID、免责声明标识。
- 失败行为：没有可靠依据时明确提示依据不足；模型或检索服务异常时返回统一错误。

### S2：多轮追问

- 示例：用户先咨询拖欠工资，随后追问“我需要准备哪些证据？”
- 输入：后续问题和原会话 ID。
- 处理：只加载当前用户对应会话的最近上下文，再执行问答流程。
- 输出：与上文相关的回答、来源和相同会话 ID。
- 隔离要求：不同用户之间、同一用户不同会话之间不得串话。

### S3：案例检索

- 示例：查找劳动报酬争议的相似案例。
- 输入：查询文本、可选领域或元数据过滤条件、返回数量。
- 处理：向量检索与基础关键词检索；首月不启用正式 Reranker。
- 输出：案例 ID、标题、案号、法院、裁判日期、领域、摘要、来源地址和相关度信息。
- 真实性要求：演示数据必须标注，真实资料必须能够追溯原始来源。

### S4：文书生成

- 示例：根据用户提供的信息生成民事起诉状草稿。
- 输入：英文文书类型标识、结构化参数、补充说明、是否参考知识库。
- 处理：参数校验、缺失信息提示、可选知识检索、模板化生成。
- 输出：文书正文、类型、引用依据、缺失项和风险提示。
- 下载范围：Markdown 和 TXT。

### S5：会话管理

- 输入：当前用户身份及会话 ID。
- 输出：当前用户自己的历史记录，或清空结果。
- 安全要求：不能通过猜测 UUID 访问其他用户会话。

## 5. 首批法律领域

首月仅覆盖：

- 婚姻家庭
- 劳动争议
- 交通事故
- 合同纠纷

领域之外的问题可以提供一般性提示，但不得伪装成已有知识库支持的结论。系统应优先说明覆盖范围并建议用户咨询专业人士。

## 6. 文书类型标识

前后端统一使用以下英文标识：

| 标识 | 中文名称 | 首月输出 |
| --- | --- | --- |
| `civil_complaint` | 民事起诉状 | Markdown、TXT |
| `civil_defense` | 民事答辩状 | Markdown、TXT |
| `general_contract` | 通用合同 | Markdown、TXT |

显示名称只用于界面，不作为接口枚举值。缺少当事人、诉讼请求、事实理由或合同核心条款等必要信息时，系统必须返回缺失项，不得自行编造。

## 7. 数据分类与来源规则

每条知识资料必须标记 `source_kind`：

- `demo`：仅用于打通开发链路的演示数据，不得声称为真实判例。
- `official`：来自法院、政府部门或国家法律法规公开渠道的资料。
- `public_reference`：来自其他可公开核验的资料，需要保留发布者和原始地址。

案例的最小字段：

- UUID
- 标题
- 案号；演示数据使用明确的演示编号，不能伪造真实案号
- 法院或明确的演示标识
- 裁判日期或样本日期
- 所属领域
- 基本事实
- 裁判理由或样本说明
- 涉及法条
- 原文来源地址
- 数据来源类别
- 是否为演示数据
- 导入时间

法条资料至少保留法规名称、条文编号、正文、发布机关、发布日期、生效状态、来源地址和抓取或导入时间。后续整理真实资料时，应核验其在使用时是否仍然有效。

## 8. 功能需求清单

### FR-AUTH：认证

- `FR-AUTH-01` 支持用户名、邮箱和密码注册。
- `FR-AUTH-02` 支持登录并签发有过期时间的 JWT。
- `FR-AUTH-03` 除健康检查和认证接口外，业务接口默认要求登录。
- `FR-AUTH-04` 密码只保存安全哈希，不保存或记录明文。
- `FR-AUTH-05` 用户 ID、业务数据 ID 和会话 ID 统一使用 UUID。

### FR-CHAT：问答与会话

- `FR-CHAT-01` 支持普通问答。
- `FR-CHAT-02` 支持 SSE 流式问答。
- `FR-CHAT-03` 每次回答返回 `intent`、`sources` 和 `session_id`。
- `FR-CHAT-04` 支持查询和清空当前用户自己的会话历史。
- `FR-CHAT-05` 来源不足时触发保守回答或拒答。

### FR-CASE：案例检索

- `FR-CASE-01` 通过 POST 请求执行案例搜索。
- `FR-CASE-02` 支持按首批四个领域和基础元数据过滤。
- `FR-CASE-03` 支持通过 UUID 获取案例详情。
- `FR-CASE-04` 检索结果明确显示演示数据标识和原始来源。

### FR-DOC：文书

- `FR-DOC-01` 支持三种固定英文类型标识。
- `FR-DOC-02` 对不同文书类型执行结构化必填参数校验。
- `FR-DOC-03` 支持复制文书正文。
- `FR-DOC-04` 支持 Markdown 和 TXT 下载。
- `FR-DOC-05` 文书必须显示草稿和人工复核提示。

### FR-DATA：知识库

- `FR-DATA-01` 支持可重复执行的清洗、分块和 Chroma 入库流程。
- `FR-DATA-02` 重复导入不会产生重复知识块。
- `FR-DATA-03` 首阶段使用少量明确标记的演示数据。
- `FR-DATA-04` 后续真实资料必须保留完整来源元数据。

## 9. 输入约束

- 所有文本输入去除首尾空白，并设置合理长度上限。
- 枚举字段只接受文档规定的固定值。
- UUID、邮箱、分页数量和过滤条件在进入业务层前完成校验。
- 不将完整用户问题、密码、Token 或 API Key 写入日志。
- 上传文件、OCR 和任意外部 URL 抓取不属于首月交互功能。

具体长度、分页和超时数值在接口设计阶段统一确定。

## 10. 统一输出约定

成功响应采用统一外壳：

```json
{
  "success": true,
  "data": {},
  "request_id": "uuid"
}
```

非流式错误采用统一结构：

```json
{
  "success": false,
  "error": {
    "code": "STABLE_ERROR_CODE",
    "message": "可供用户理解的错误信息",
    "details": null
  },
  "request_id": "uuid"
}
```

SSE 使用具名事件，至少包含 `meta`、`content`、`sources`、`error` 和 `done`。流开始后发生的错误通过 `error` 事件返回，不再尝试改写 HTTP 状态码。

## 11. 免责声明

免责声明按使用时机分层呈现，避免在主流程中重复堆叠。产品界面仅保留以下三个固定触点：注册或首次使用、咨询输入框下方、每次回答底部。

### 11.1 注册或首次使用时的完整版本

完整版只在用户注册或首次使用时展示一次，不在登录主流程中重复出现。

> 本系统由人工智能生成内容，仅提供一般法律信息，不构成法律意见、律师服务或任何结果保证。AI 可能产生错误、遗漏或过时信息；在采取行动前，请核对法规、案例等原始依据。涉及诉讼时效、举证期限、重大财产、人身安全或其他重要权益时，请及时咨询执业律师或有关机关。请勿提交身份证号码、银行卡号、完整住址等非必要敏感信息。

### 11.2 咨询输入框固定短版

> AI 生成内容仅供参考，不构成法律意见。重要事项请核对原始依据或咨询专业人士。

### 11.3 回答和文书提示

- 每次回答底部设置单一“依据与提示”区域，集中显示来源状态、核验提示和风险提示，避免连续出现多条重复免责声明。
- 未返回可核验来源时必须明确说明；只有真实返回来源详情后，才能提供“查看参考依据”等入口。
- 演示数据来源必须显示“演示数据，不是真实判例”。
- 文书顶部显示“草稿，提交或签署前须人工审核”。
- 紧急、人身安全或即将超过法定期限的情况，优先提示用户及时联系有关机关或律师。

### 11.4 首页和页脚

- 首页不再展示整块免责声明，只保留面向任务的产品说明和直接咨询入口。
- 公共页脚只提供“使用说明”“隐私说明”“关于我们”三个入口，不重复展示免责声明正文。
- 完整使用边界、隐私和项目背景分别放入对应说明页面；课程属性不得反复占据产品主流程。

## 12. 非功能要求

- 配置：开发和生产配置分离，API Key 只从环境变量读取。
- 安全：`.env` 必须进入 `.gitignore`；敏感字段不得出现在代码、日志或错误详情中。
- 可测试：模型调用通过抽象接口注入，自动化测试使用确定性的假模型。
- 可追踪：每个请求生成 `request_id`，回答来源包含稳定标识。
- 可恢复：DeepSeek、Redis、PostgreSQL 或 Chroma 不可用时返回明确错误。
- 可部署：最终通过 Docker Compose 在 Windows Docker Desktop 上启动。
- 可复现：README 记录环境配置、启动、导入、测试和演示步骤。

## 13. 首月不做清单

- 管理后台和管理员角色体系
- MinIO 或其他对象存储
- OCR、文件上传和文档解析界面
- Milvus、Pinecone 等额外向量数据库
- 同时接入多个 LLM 提供商或运行时模型切换
- 正式 Reranker 与大型本地推理模型
- DOCX、PDF 文书导出
- 律师撮合、在线委托、支付或付费功能
- 面向公众的生产级发布、高可用集群和真实数据迁移
- 超出四个首批领域的专项法律知识库
- 自动替用户提交文书、联系机构或执行任何外部法律行为

## 14. 首月最终技术约束

本节定义四周目标架构；当前SQLite、Redis及Chroma的使用方式见[系统架构](architecture.md)。

- API 前缀统一为 `/api/v1`。
- 后端使用 FastAPI、Pydantic、SQLAlchemy 和 Alembic。
- Agent 工作流使用 LangGraph，意图限定为 `qa`、`search`、`document`。
- LLM 使用 DeepSeek OpenAI 兼容接口，连接信息通过环境变量提供。
- Chroma 只采用本地持久化模式，不启动独立 Chroma 服务。
- PostgreSQL 保存用户、案例元数据和生成记录；Redis 保存短期会话数据。
- 前端使用 Vue 3、Vite、Pinia、Axios 和 Tailwind CSS。
- API、数据库和会话标识统一使用 UUID。

## 15. 界面约束

- 保留“衡”字图标、深墨绿与米白配色、响应式布局和无障碍能力。
- 首页以问题输入、功能入口和四个支持领域为主；登录页在移动端优先呈现表单。
- 咨询页围绕当前任务组织，保留消息、来源、错误重试和确认入口；不反复展示工程信息。
- 免责声明按第11节分层呈现；公共页脚提供使用说明、隐私和关于页面。
- 未接入能力标明“即将开放”或不提供交互，不用占位数据冒充真实功能。

## 16. 法条与多轮要求

- 四领域问答补事实和三类文书补字段均在范围内。每轮最多追问三项；冲突先确认，不静默覆盖。
- 法条经官方来源核验后本地入库、人工更新，分别记录公布、生效、核验及资料状态截止日期。当前有效不等于适用历史事件，资料缺失时明确不足。
- 法规名称、条号、版本、原文和链接由服务端提供；模型结论须有对应原文支持。合成案例不作为法律依据。
- 任务保留字段原句和用户消息来源，与历史共享24小时滑动TTL、互斥及失败补偿。过期重新补充，不从其他会话恢复事实。
- 文书补齐后展示摘要，经用户确认才生成；支持更正、取消、重启，原文书不覆盖。同步与流式共用校验，最终保存成功才确认完成。

详细流程见[多轮设计](legal-multiturn.md)，协议见[API合同](api-contract.md)。历史验收记录保留在[acceptance目录](acceptance)，不作为当前需求清单。
